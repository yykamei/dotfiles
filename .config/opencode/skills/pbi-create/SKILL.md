# プロダクトバックログアイテム作成

スクラムの**プロダクトバックログアイテム (PBI)** を、ユーザーとの対話を通じて作成するスキルです。

## 使い方

このスキルは 2 通りの起動方法に対応します。

### 1. 通常の対話で起動する

ユーザーが「PBI を作りたい」「バックログアイテムを起票したい」と
依頼してきた場合、エージェントがこのスキルをロードし、対話の冒頭で
ビジネス面での要求（実現したいこと・課題）をユーザーに尋ねます。

### 2. slash command として起動する（任意）

slash command を併設している環境では以下の形式が使えます:

```bash
/pbi-create [実現したいこと・課題]
```

例:

```bash
/pbi-create ワーカーが勤怠実績を自分で確認できるようにしたい
```

```bash
/pbi-create 企業が募集条件を柔軟に変更できるようにしたい
```

**ポイント**: 引数や依頼内容には「how（どう実現するか）」ではなく
「what/why（何を実現したいか・なぜ必要か）」を伝えてください。

1 回の依頼から複数の PBI が生成されることがあります。その場合も、各 PBI は原則として単独で価値を提供できる単位になります。

## 出力フォーマット

最終的に以下のフォーマットで各 PBI を Markdown として出力します。

### 文体ルール

**出力する Markdown の本文（特に「概要」セクション）は、すべて「です・ます調」で記述すること。「だ・である調」は使わない。**

- 良い例: 「〜という課題があります。」「〜できるようにします。」「〜が必要です。」
- 悪い例: 「〜という課題がある。」「〜できるようにする。」「〜が必要だ。」

> 受入基準の項目は「〜できること」「〜が担保されていること」のような体言止め形式で記述するため、このルールの対象外です。起こったら困ることの箇条書きも「〜する可能性」「〜のリスク」のような名詞句や体言止めで記述してください。ただし、完全な文で書く場合は「です・ます調」に従ってください。

### テンプレート

```markdown
# 概要

[です・ます調で記述します。背景・課題・解決策を記述します。例: 「現状、〇〇という課題があります。これを解決するために、△△が□□できるようにします。」]

## ターゲットユーザー

[この変更で価値を受け取るユーザーを、です・ます調の自然な文章で記述します。]

## アウトカム

[この PBI が実現された場合の成功状態を、です・ます調の自然な文章で記述します。]

## 依存関係

[依存関係が避けられない場合のみ、このセクションを追加します。依存先の PBI 名と、依存が必要な理由を記載します。依存関係がない場合はこのセクション自体を作りません。]

# 受入基準

- [ ] [体言止め形式。例: 「〜できること」「〜が担保されていること」]
- [ ] ...

# 起こったら困ること

- [簡潔な箇条書き]
- ...
```

依存関係がない場合は `## 依存関係` を省略します。

### 出力例

以下は「です・ます調」で記述された PBI の具体例です。概要セクションの文体を参考にしてください:

```markdown
# 概要

現状、ワーカーは自分の過去の勤怠実績を確認する手段がなく、勤務時間や出勤日数について問い合わせが発生しています。これを解決するために、ワーカーが自分の勤怠実績一覧を画面上で確認できるようにします。

## ターゲットユーザー

この機能の主なターゲットユーザーは、自身の勤怠状況を把握したいワーカーです。

## アウトカム

ワーカー自身が勤怠状況をいつでも確認でき、問い合わせ対応の負荷が軽減されている状態を目指します。

# 受入基準

- [ ] ワーカーが過去の勤怠実績一覧を確認できること
- [ ] 勤怠実績が日付順に表示されること
- [ ] 対象期間を絞り込んで表示できること

# 起こったら困ること

- 他のワーカーの勤怠実績が閲覧できてしまう可能性
- 既存の勤怠登録機能へのデグレ
```

#### もう 1 つの例（企業向け）

```markdown
# 概要

現状、企業が一度公開した募集条件を変更するには、運営への問い合わせが必要であり、応募状況の変化に応じた柔軟な調整ができていません。これを解決するために、企業が自身で募集条件を編集できるようにします。

## ターゲットユーザー

このスキルが価値を提供する主なターゲットユーザーは、自社の募集条件を運用しながら最適化したい企業の採用担当者です。

## アウトカム

応募が想定より少ない・多いといった状況に対し、企業が自律的に募集条件を見直せる状態を目指します。あわせて、運営への変更依頼問い合わせが減少することも期待します。

# 受入基準

- [ ] 企業の採用担当者が公開済みの募集条件を編集できること
- [ ] 編集内容が応募者向け画面に正しく反映されること
- [ ] 編集履歴が運営側から追跡できること

# 起こったら困ること

- 既に応募済みのワーカーに不利な条件変更が行われる可能性
- 公開中の他社募集に意図せず影響が及ぶデグレ
```

### 圧縮と分割の例

受入基準は、同じ対象・同じ条件でまとめても検証可能性が落ちない場合に圧縮します。

```markdown
圧縮前:
- [ ] 勤怠実績一覧に日付が表示されること
- [ ] 勤怠実績一覧に勤務時間が表示されること

圧縮後:
- [ ] 勤怠実績一覧に日付と勤務時間が表示されること
```

受入基準が 8 件以上、または起こったら困ることが 6 件以上になった場合は、次のような分割案を提示します。

| PBI 名 | スコープ | 受入基準 | 起こったら困ること | 依存関係 |
| --- | --- | --- | --- | --- |
| 勤怠実績の日次確認 | ワーカーが日次の勤怠実績を確認できる | 4 件 | 2 件 | なし |
| 勤怠実績の月次確認 | ワーカーが月次の勤怠実績を確認できる | 4 件 | 2 件 | なし |

この表は分割案の概要です。分割案では、元の受入基準がどの PBI に割り当てられるかも示し、漏れがないことを確認します。

依存関係が避けられない場合は、依存する側の PBI の `# 概要` 内に次のように記載します。この例では、編集履歴の追跡 PBI が募集条件の編集 PBI に依存しています。

```markdown
## 依存関係

- 募集条件の編集: 編集履歴を表示するには募集条件を編集できる必要があるため、先に完了している必要があります。
```

### 各セクションのガイドライン

- **概要**: 背景・課題・解決策を**です・ます調の自然な文章**で記述します。加えて、以下のサブセクションを設けます:
  - **ターゲットユーザー**: この変更で価値を受け取るユーザーを、です・ます調の自然な文章で明記します
  - **アウトカム**: この PBI が実現された場合の成功状態を、です・ます調の自然な文章で明記します
- **受入基準**: 「満たしたい状態」を定義します。実装の詳細（API設計、DB設計、具体的なUI要素など）には踏み込みません。「〜できること」「〜が担保されていること」のような体言止め形式で記述します
- **起こったら困ること**: デグレや意図しない副作用を中心に、簡潔な箇条書きで記述します
- **依存関係**: 依存関係が避けられない場合のみ、`# 概要` 配下に `## 依存関係` を追加し、依存先の PBI 名と理由を記載します。依存関係がない場合は省略します

## PBI のサイズ管理

### 閾値

- 受入基準は 7 件以内とする。8 件以上は分割を検討する
- 起こったら困ることは 5 件以内とする。6 件以上は分割を検討する
- 受入基準は `- [ ]` の項目数、起こったら困ることは `-` の項目数で数える
- 受入基準は圧縮後の件数で判定する
- 起こったら困ることは、重複を排除した後の件数で判定する

### 受入基準の圧縮

- 閾値判定の前に、必ず圧縮できる項目がないか確認する
- 圧縮は、同じ対象・同じ条件で、まとめても検証可能性が落ちない場合に限る
- 例: 「AにBが表示されること」「AにCが表示されること」→「AにBとCが表示されること」
- 圧縮前後の件数と内容をユーザーに提示し、承認を得る。勝手に圧縮しない
- 圧縮候補がない場合は、その旨をユーザーに伝える
- ユーザーが圧縮を拒否した場合は、原文のまま件数を数えて閾値判定に進む
- 受入基準を追加・修正した場合は、圧縮と件数確認をやり直す

### PBI 分割

- 受入基準が 8 件以上、または起こったら困ることが 6 件以上の場合、分割案を提示する
- 分割は、ユーザーから見える価値の単位で行う。DB・API・UI などの技術レイヤーでは分割しない
- 各 PBI は、原則として単独で自らの受入基準を満たし、ユーザーに価値を提供できる単位にする。依存関係が避けられない場合は、その依存関係を明記する
- 単なる作業ステップや、1 つの受入基準だけの PBI に分割しない。分割しすぎない
- 分割案には、PBI 名、スコープ、受入基準件数、起こったら困ることの件数、依存関係を一覧で示す（例は「圧縮と分割の例」を参照）
- 元の受入基準がどの PBI に割り当てられるかを示し、漏れがないことを確認する
- 元の「起こったら困ること」がどの PBI に関係するかを確認し、必要なリスクが漏れていないことを確認する
- 各 PBI が閾値以内になるまで分割する。受入基準が 7 件以下にならない場合は、分割案を再検討し、それでも解消しないときはユーザーに相談する
- 共通リスクにより 5 件を超える場合は、各 PBI に必要なリスクをすべて記載し、完了報告で超過理由を明記する。共通リスクを代表 PBI だけに記載して、他の PBI から省略しない
- 分割軸を見直しても PBI 固有のリスクが 6 件以上残る場合は、その旨と理由を分割案に明記し、ユーザーの承認を得てから出力する
- 分割案はユーザーの承認を得てから確定する
- ユーザーが分割案を拒否した場合は修正して再承認を得る。ユーザーが明示的に 1 つの PBI を望む場合はそれに従い、例外として理由を記録する
- 分割が PBI として成立しない場合は、1 つの PBI に留め、その理由と閾値超過を明記してユーザーに相談する

### 依存関係

- 分割後の PBI は、依存関係を持たせないことを原則とする
- 依存関係とは、ある PBI が、他の PBI の完成なしには自らの受入基準を満たせない、または価値を提供できない状態を指す。実装順序の推奨や、同じ画面を触ることは依存関係とみなさない
- 依存関係を持たせるのは最終手段とする。まず、依存なしで価値を出せるように分割軸を見直す
- どうしても依存関係が避けられない場合は、依存する側の PBI の `# 概要` 配下に `## 依存関係` を追加し、依存先の PBI 名（可能ならファイル名）および理由を記載する
- 依存関係がない PBI には `## 依存関係` を作らない

## 実行フロー

```
Progress:
- [ ] Phase 1: 意図の深掘り
- [ ] Phase 2: 受入基準と起こったら困ることの整理（圧縮を含む）
- [ ] Phase 3: 閾値判定と PBI 分割案の承認
- [ ] Phase 4: PBI の出力とレビュー
```

### Phase 1: 意図の深掘り

ユーザーが与えた引数をもとに、PBI の「概要」セクションを書くために必要な情報を質問で明確にする。

以下の観点が不明確な場合、質問して確認する。関連する観点は `question` ツールを使って1回の質問にまとめてよい:

1. **What（何をしたいのか）**: 実現したい機能や変更の本質
2. **Why（背景）**: なぜ今それが必要なのか、どんな課題やペインがあるのか
3. **Who（対象ユーザー）**: この変更で価値を受け取るのは誰か（ワーカー、企業、社内オペレーターなど）
4. **Outcome（最終的なアウトカム）**: これが実現された場合、どんな状態になれば成功と言えるか

引数から十分に読み取れる情報については質問を省略してよい。すべてが明確な場合はこのフェーズをスキップできる。

### Phase 2: 受入基準と起こったら困ることの整理（圧縮を含む）

Phase 1 で得た情報をもとに、受入基準と起こったら困ることを整理する。

**受入基準について**:

- まずエージェント側で受入基準の案を提示し、ユーザーに過不足を確認する
- 「満たしたい状態」として定義する（例: 「ワーカーが過去の勤怠実績一覧を確認できること」）
- 実装の詳細には踏み込まない（例: NG「REST API で GET /attendances を実装する」）
- 不足している観点があればユーザーに質問する
- 案が出たら、「PBI のサイズ管理」の圧縮ルールに従って圧縮候補を確認する
- 圧縮候補があれば圧縮前後の件数と内容を提示し、承認を得る。候補がない場合はその旨を伝える
- 圧縮の承認後（候補がない場合、またはユーザーが圧縮を拒否した場合はそのまま）、`- [ ]` の数を数える。8 件以上なら Phase 3 に進む

**起こったら困ることについて**:

- 既存機能へのデグレや意図しない副作用を中心にヒアリングする
- エージェント側でも想定されるリスクを提示し、ユーザーに確認する
- 箇条書きで簡潔に記述する
- 重複や一般論を排除し、PBI 固有のリスクに絞る
- `-` の数を数える。6 件以上なら Phase 3 に進む

受入基準が 7 件以下かつ起こったら困ることが 5 件以下なら、Phase 3 をスキップして Phase 4 に進む。

### Phase 3: 閾値判定と PBI 分割案の承認

Phase 2 で閾値を超えた場合、以下の手順で分割案を作る。

1. ユーザーから見える価値の単位で分割軸を決める
2. 各 PBI にタイトル、スコープ、受入基準、起こったら困ることを割り当て、元の受入基準と元の「起こったら困ること」に漏れがないか確認する
3. 各 PBI の件数を数え、受入基準が 8 件以上ならさらに分割する。起こったら困ることが 6 件以上なら分割軸を見直す。共通リスクで 5 件を超える場合、または分割軸を見直しても PBI 固有のリスクが 6 件以上残る場合は、その旨と理由を分割案に明記し、ユーザーの承認を得る
4. 各 PBI が単独で価値を提供できるか確認する。依存関係がある場合は依存先の PBI 名と理由を明記し、依存関係が最終手段であることをユーザーに伝える
5. 分割案を一覧で提示し、承認を得る（一覧の例は「圧縮と分割の例」を参照）。承認されるまで本文を書かない
6. 修正が必要な場合は修正後に再度承認を得る

### Phase 4: PBI の出力とレビュー

- 出力フォーマットに従って、各 PBI を Markdown で出力する
- 分割した場合は、PBI ごとに個別ファイルを作成する。インデックスファイルは作らない
- 各ファイルのスラッグは PBI ごとに変える（例: `pbi-20261108-worker-attendance-daily.md`, `pbi-20261108-worker-attendance-monthly.md`）
- `-2`, `-3` は既存ファイルとの衝突回避にのみ使い、分割した兄弟 PBI の区別には使わない
- **各 PBI の概要セクション（ターゲットユーザー・アウトカム・依存関係のサブセクションを含む）は必ず「です・ます調」で記述する。出力前に文体を確認し、「だ・である調」の文が含まれていないことを確かめる**。具体的には、文末が「〜だ。」「〜である。」「〜する。」「〜なる。」「〜した。」「〜となる。」「〜必要だ。」などになっていないかチェックし、「〜です。」「〜します。」「〜なります。」「〜しました。」「〜必要です。」などに修正する
- 各 PBI の出力前に `naturalize-japanese` スキルを `本文のみモード（text-only mode）` で適用する（利用可能な場合）。本スキルの文体ルール（です・ます調、受入基準の体言止めなど）を優先し、質問はせず、迷ったら残す。確認点は PBI 本文には入れず、完了報告に短く添える
- すべての PBI をユーザーにレビューしてもらい、修正が必要な場合は対応する
- レビューでの修正で閾値を超えた場合は、Phase 3 に戻って分割案の承認を得てから保存する
- 出力先は `~/.pbi/` とし、ファイル名は次のテンプレートに従う:

  ```
  ~/.pbi/pbi-YYYYMMDD-<英数字スラッグ>.md
  ```

  - `YYYYMMDD` は作成日（ローカル日付）
  - スラッグはタイトルを英数小文字 + ハイフンで要約したもの（最大
    40 文字程度）。日本語タイトルの場合はローマ字または英訳した短い
    キーワードを用いる
  - 例: `~/.pbi/pbi-20260425-worker-attendance-view.md`,
    `~/.pbi/pbi-20260425-company-flexible-recruitment.md`
- 保存先の `~/.pbi/` が存在しない場合は作成する（`mkdir -p ~/.pbi`）
- 既存ファイルが存在する場合は上書きせず、末尾に `-2`, `-3` のような
  連番を付けて区別する
- 完了報告に、作成したファイルの一覧、依存関係の有無、閾値を超えた PBI とその理由（受入基準・起こったら困ることの両方）、およびユーザーの承認を得た例外を記載する

---

## インタラクションの原則（最重要）

このスキルでは、**ユーザーとの対話を最大限に重視**します。

- **推測せず必ず質問する**: AI エージェントはユーザーの背景情報を持っていない。曖昧な表現や複数の解釈が可能な場合は、自分の解釈で進めず必ず質問する
- **関連する質問はまとめる**: `question` ツールを活用し、関連する質問は1回の呼び出しにまとめて聞く。ただし、前の回答に依存する質問は分けて順番に聞く
- **納得するまで先に進まない**: すり合わせが不十分なまま次のフェーズに進まない。ユーザーの意図を十分に理解できたと確信してから PBI を生成する
- **Few-shot による改善に頼らない**: 出力後に修正を繰り返すのではなく、事前の質問で正しい方向性を確立する
- **圧縮・分割は勝手に確定しない**: 圧縮案と分割案は、必ずユーザーに提示して承認を得る
- **依存関係を安易に作らない**: 分割案を出す前に、各 PBI が単独で価値を提供できるか確認する。依存関係は最終手段
- **閾値を超えたまま出力しない**: 受入基準が 8 件以上、または起こったら困ることが 6 件以上なら分割案を提示する。ユーザーの明示的な指示や相談の結果として承認された場合、および共通リスクによる超過は、理由を明記して許容する
